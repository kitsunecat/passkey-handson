# お題5：本人確認フラグ（UV）と二要素認証

## 目的

- 本人確認フラグ（UV）が何を表すかを理解する
- 本人確認を必須にするにはサーバーでの検証が必要なことを理解する
- 検証の設定を途中で緩めさせない実装を知る
- 本人確認フラグの限界を理解し、二要素認証を省略してよいかを考える

## セッションとの対応

セッションの「パスキーと二要素認証」の話。本人確認フラグが認証器の自己申告であることを確かめ、パスキーでログインしたときに二要素認証を省略してよいかを考えます。

本人確認フラグ（UV：User Verified）は、認証器が指紋・顔・PIN などで本人確認をしたかどうかを表す。
`user_verification` の値は、required＝本人確認を必ずする、preferred＝できればする、discouraged＝しなくてよい、という意味。

## AIへの指示例

> `user_verification` を required / preferred / discouraged で切り替えられる設定を追加して。required のときは、サーバー側でも本人確認フラグ（UV）を検証し、`false` ならログインを拒否して。preferred / discouraged で本人確認フラグが `false` のときは、二要素目としてワンタイムコードの入力を求めて（コードは固定値でよい）。
> 本人確認をしない認証器を再現するため、「届いた本人確認フラグをサーバー側で `false` とみなす」設定も追加して。ログイン後の画面には、設定・本人確認フラグ・ワンタイムコードを入力したかを表示して

## 確認方法

仮想認証器はいつもの設定（user verification オン）のまま、「本人確認を求めるか」と「本人確認しない認証器を再現する」を切り替えてログインする。

| 本人確認を求めるか | 再現オフ | 再現オン |
| --- | --- | --- |
| 必ず求める（required） | ワンタイムコードなしでログイン | ログインを拒否する |
| できれば求める（preferred） | ワンタイムコードなしでログイン | ワンタイムコードの画面 |
| 求めない（discouraged） | ワンタイムコードなしでログイン | ワンタイムコードの画面 |

- 再現オフでは、どの設定でも本人確認フラグ = `true` で届く（`discouraged` でも仮想認証器は本人確認をする）
- 再現オンで本人確認フラグが `false` になると、`required` はサーバーの検証で拒否され、`preferred` / `discouraged` は所持の一要素だけなので、ワンタイムコードを求められる

そのうえで「本人確認なしの認証を拒否するか、二要素目を求めるか」「本人確認フラグは認証器の自己申告だが、それでも二要素認証を省略してよいか」を議論する。

> Chrome の仮想認証器は `discouraged` でも本人確認をして、本人確認フラグを `true` で返します。また「Supports user verification」をオフにすると、ユーザーネームレスのログインそのものが拒否されてしまいます。そのため、本人確認フラグが `false` の認証は「本人確認しない認証器を再現する」設定で作ります。
