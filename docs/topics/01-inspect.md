# お題1：中身を覗く（全員）

## 目的

サーバーに届くのは公開鍵と署名だけであることを確認する。
また、サーバーが毎回作る使い捨てのランダムな値（チャレンジ）のおかげで、同じデータを送り直してもログインできない（リプレイ攻撃を防げる）ことを確認する。

## 講演との対応

登録・ログインの流れ、使い捨てのランダムな値（チャレンジ）の説明。

## AIへの指示例

> 登録時と認証時に、サーバーが生成したオプションと、ブラウザから届いたデータ（クレデンシャルID、AAGUID、UP/UVフラグ、sign_count）をわかりやすく画面とログに表示して。同じ認証データをもう一度送る『リプレイ』ボタンも付けて

## 確認方法

- 秘密鍵はどこにも出てこないこと
- ログインのたびに sign_count（パスキーを使った回数）や challenge（ランダムな値）が変わること
  - 仮想認証器は sign_count を1ずつ増やします。iCloud キーチェーンなど同期されるパスキーは常に 0 のことがあります
- リプレイボタンでは検証が失敗すること

## 補足：表示される値の意味

| 値 | 意味 |
| --- | --- |
| クレデンシャルID | パスキーごとの ID。ログイン時にどのパスキーかを見分けるのに使う |
| UP フラグ | ユーザーが認証器を操作した（タッチしたなど）か（User Present） |
| UV フラグ | 指紋・顔・PIN などで本人確認をしたか（User Verified） |
| sign_count | パスキーを使った回数。前回より増えていなければ、コピーされたパスキーの疑いがある |

## 補足：AAGUID

仮想認証器を2つ作ってそれぞれで登録すると、AAGUID が同じ値になります。
AAGUID は個人ではなく、認証器の「種類」を表す ID です。SmartHR はこれを認証器名に変換して、パスキーの初期名にしています（意思決定6）。
