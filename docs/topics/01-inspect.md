# お題1：中身を覗く（全員）

## 目的

- 秘密鍵が認証器の外に出ないことを理解する
- サーバーが毎回作る使い捨てのランダムな値（チャレンジ）が、同じデータの送り直し（リプレイ攻撃）を防ぐ仕組みを理解する
- 署名にオリジン（どのサイトで操作したか）が含まれる意味を理解する
- AAGUID が何を表すかを知る

## セッションとの対応

セッションの「パスキーとは」と「登録・ログインの流れ」の話。秘密鍵はサーバーに送られず公開鍵だけが保存されること、チャレンジでリプレイ攻撃を防ぐことを、実際のデータで確かめます。

## AIへの指示例

> 登録時と認証時に、サーバーが生成したオプションと、ブラウザから届いたデータ（クレデンシャルID、AAGUID、UP/UVフラグ、sign_count）をわかりやすく画面とログに表示して。同じ認証データをもう一度送る『リプレイ』ボタンも付けて

## 確認方法

- 秘密鍵はどこにも出てこないこと
- ログインのたびに sign_count（パスキーを使った回数）や challenge（ランダムな値）が変わること
  - 仮想認証器は sign_count を1ずつ増やします。iCloud キーチェーンなど同期されるパスキーは常に 0 のことがあります
- リプレイボタンでは検証が失敗すること

## 補足：表示される値の意味

| 値 | 意味 |
| --- | --- |
| クレデンシャルID | パスキーごとの ID。ログイン時にどのパスキーかを見分けるのに使う |
| UP フラグ | ユーザーが認証器を操作した（タッチしたなど）か（User Present） |
| UV フラグ | 指紋・顔・PIN などで本人確認をしたか（User Verified） |
| sign_count | パスキーを使った回数。0 以外の値で前回より増えていなければ、コピーされたパスキーの疑いがある（同期されるパスキーは常に 0 なので判定に使えない） |

## 補足：AAGUID

仮想認証器を2つ作ってそれぞれで登録すると、AAGUID が同じ値になります。
AAGUID は個人ではなく、認証器の「種類」を表す ID です。SmartHR はこれを認証器名に変換して、パスキーの初期名にしています（セッションの「登録したパスキーをどう識別するか」の話）。
